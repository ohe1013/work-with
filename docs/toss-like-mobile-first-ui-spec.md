# Toss-like Mobile-First Map Product UI Spec

> 비주얼 밀도와 강조 방식은 `docs/toss-like-minimal-visual-override.md`의 오버라이드 규칙을 함께 적용한다.

## 0. 문서 목적

이 문서는 운동 메이트 서비스의 UI를 설계하거나 생성할 때 사용하는 기준 문서다.

목표는 다음과 같다.

- 토스라이크한 정돈감과 명확한 정보 위계를 가진다
- 모바일에서 특히 읽기 쉽고 누르기 쉬운 화면을 만든다
- 지도 중심 제품의 특성을 살린다
- 금융앱 복제처럼 보이지 않도록 제품 맥락에 맞게 재해석한다
- 홈, 찾기, 등록, 로그인 화면이 하나의 일관된 디자인 언어로 이어지게 한다

---

## 1. 방향 정의

여기서 "Toss-like"는 토스 앱의 특정 화면을 복제한다는 뜻이 아니다.  
아래의 제품 디자인 원칙을 참고한다.

- 정보 위계가 한눈에 보인다
- CTA가 선명하다
- 여백이 충분하다
- 카드, 폼, 리스트가 정돈되어 있다
- 사용자가 지금 무엇을 해야 하는지 바로 이해된다
- 모바일에서 특히 읽기 쉽고 누르기 쉽다
- 장식보다 사용성, 속도, 명확성을 우선한다

이 문서의 목적은 "토스 복제"가 아니라  
**운동 메이트 서비스에 맞는, 깔끔하고 신뢰감 있는 모바일 우선 UI**를 만드는 것이다.

---

## 2. 제품 맥락

이 제품은 운동 메이트를 찾고, 등록하고, 신청하는 서비스다.

### 핵심 사용자 과업

- 근처 운동 메이트 찾기
- 지도에서 위치와 모집 정보를 빠르게 파악하기
- 조건을 조정해 원하는 모임 찾기
- 직접 운동 모임을 등록하기
- 로그인 후 신청 흐름으로 자연스럽게 이어지기

### 핵심 UX 목표

- 지도는 주 경험이고, 리스트와 상세는 보조 경험이다
- 사용자는 탐색 → 비교 → 신청까지 빠르게 이동할 수 있어야 한다
- UI는 건강/운동 서비스답게 가볍고 명확해야 하며, 금융앱처럼 보이면 안 된다
- 모바일에서는 한 손 사용성이 좋아야 하고, 데스크톱에서는 정보 탐색 효율이 좋아야 한다

---

## 3. 금지 사항

- 토스 앱의 문구, 화면 구성, 디테일을 그대로 복제하지 않는다
- 운동 메이트 서비스와 무관한 금융앱식 정보 구조를 억지로 끼워 넣지 않는다
- 장식성만 높은 UI를 우선하지 않는다
- 랜딩페이지처럼 보이게 만들지 않는다
- 제품 맥락 없는 마케팅 문구를 남발하지 않는다
- 지도보다 카드 UI가 더 주인공처럼 보이게 만들지 않는다

---

## 4. AI 템플릿 스타일 금지

아래 요소는 특별한 근거가 없으면 사용하지 않는다.

- 과한 그라데이션 배경
- 전체 화면 글래스모피즘
- 의미 없이 둥근 카드가 반복되는 2x2 / 3x1 그리드
- "Features / Testimonials / CTA" 식의 전형적인 SaaS 랜딩페이지 구조
- 금융앱처럼 보이는 과도한 요약 카드
- 필요 이상으로 많은 배지, 아이콘, 상태칩
- 장식용 일러스트, 이모지, 과한 하이라이트
- 기본 느낌의 무난한 SaaS 색조 조합
- 제품 맥락 없는 "시작하기", "더 알아보기", "지금 경험해보세요" 같은 모호한 CTA
- Lorem ipsum, 가짜 후기, 의미 없는 placeholder 데이터
- 화면마다 지나치게 다른 스타일
- 이유 없는 과장된 애니메이션
- 지도 서비스인데 지도보다 패널과 카드가 더 눈에 띄는 구성

---

## 5. 핵심 레이아웃 원칙

### 모바일

- 상단: 간결한 헤더 + 현재 상태 또는 필터 진입점
- 본문: 지도 중심
- 하단: 결과 리스트 또는 상세 정보용 바텀시트
- CTA: 등록 / 신청 / 로그인 등 핵심 액션은 엄지 도달 범위 안에 배치
- 필터와 검색은 최소 동선으로 접근 가능해야 한다
- 한 화면에 너무 많은 정보 계층을 넣지 않는다

### 데스크톱

- 좌측: 탐색 패널(검색, 필터, 목록, 상세)
- 우측: 지도
- 모바일에서 쓰는 컴포넌트를 그대로 확장해서 사용
- 데스크톱 전용 별도 제품처럼 보이면 안 된다
- 좌측 패널과 우측 지도는 시각적으로 균형이 맞아야 한다
- 상세 정보 진입 시 정보 과밀이 아니라 구조적 확장처럼 보여야 한다

### 공통

- 지도는 항상 주인공이어야 한다
- 리스트와 상세는 지도 탐색을 보조해야 한다
- 사용자는 "어디서 찾고, 무엇을 보고, 어떻게 신청하는지"를 즉시 이해할 수 있어야 한다

---

## 6. 디자인 토큰 기준

### 색

- 배경: 밝고 깨끗한 중립 배경
- 표면: 카드 / 시트 / 모달용 흰색 또는 약한 톤 분리
- 텍스트: 본문 대비가 확실한 짙은 텍스트
- 포인트: 신뢰감 있는 블루 계열 CTA
- 상태 색상: 성공 / 주의 / 에러는 최소한으로 명확하게
- 지도 위 패널은 배경과 충분히 분리되어야 한다
- 색으로만 의미를 전달하지 않는다

### 타이포

- 제목은 크게, 본문은 읽기 쉽게
- 한 화면에 제목 계층을 2~3단계 내로 제한
- 지도 위 오버레이 텍스트는 짧고 강하게
- 라벨, 보조설명, 상태텍스트는 역할이 명확하게 구분되어야 한다
- 텍스트는 광고 문구처럼 보이기보다 제품 UI처럼 보여야 한다

### 간격

- 카드 내부 상하 여백을 충분히 확보
- 폼 필드 간격은 촘촘하지 않게
- 모바일에서 탭 타깃은 최소 44px 이상
- 컴포넌트 간 간격은 규칙적으로 반복되어야 한다
- 정보 묶음 간 간격과 내부 요소 간 간격을 구분해야 한다

### 모서리와 그림자

- 카드 / 시트는 과하지 않은 라운드
- 그림자는 아주 약하게, 층위 구분에만 사용
- 지도 위 패널은 표면감이 느껴져야 함
- 입체감은 최소한으로 쓰고, 정돈감이 우선이다

---

## 7. 컴포넌트 우선순위

1. App shell
2. Header
3. Button
4. Input / Search field
5. Filter chip
6. Card
7. Empty / Loading / Error state
8. Bottom sheet / Side panel
9. Detail section
10. Form section

### 컴포넌트 공통 원칙

- 컴포넌트는 시각적으로 예쁘기보다 역할이 명확해야 한다
- 상태 변화가 분명해야 한다
- 같은 역할의 컴포넌트는 화면마다 스타일이 크게 달라지지 않아야 한다
- 작은 컴포넌트부터 쌓아 올렸을 때 전체가 자연스럽게 이어져야 한다

---

## 8. 화면별 UX 원칙

### 홈 / 탐색

- 지도가 주인공이어야 한다
- 리스트와 상세는 지도 보조 경험이어야 한다
- 검색과 필터는 바로 접근 가능해야 한다
- 첫 진입 시 "무엇을 할 수 있는지" 3초 안에 이해되어야 한다
- 현재 위치 또는 관심 지역을 기준으로 탐색이 자연스럽게 시작되어야 한다

### 찾기

- 결과 비교가 쉬워야 한다
- 조건 변경이 쉬워야 한다
- 빈 결과일 때 대안을 제시한다
- 지도 핀과 리스트 항목의 연결이 자연스러워야 한다
- 신청까지 이어지는 흐름이 끊기지 않아야 한다

### 등록

- 한 번에 긴 폼을 쏟아내지 않는다
- 장소, 시간, 운동 종류, 모집 조건을 단계적으로 정리한다
- 제출 직전 요약을 보여준다
- 사용자는 현재 어느 단계에 있는지 알아야 한다
- 입력 실수는 뒤늦게 발견되지 않도록 중간 피드백을 준다

### 로그인

- 필드 수를 최소화한다
- 에러 메시지는 짧고 정확하게 쓴다
- 데모 계정 안내와 로그인 후 복귀 동선을 명확히 둔다
- 로그인 자체가 목적처럼 보이지 말고, 신청을 위한 관문처럼 보여야 한다

### 상세

- 핵심 정보가 먼저 보여야 한다
- 위치, 시간, 운동 종류, 모집 조건, 신청 가능 여부를 빠르게 파악할 수 있어야 한다
- 신청 CTA는 스크롤을 많이 하지 않아도 보이거나 쉽게 도달 가능해야 한다
- 정보 블록이 단순 나열이 아니라 읽기 순서가 있는 구조여야 한다

---

## 9. 상태 설계 필수 규칙

각 화면은 아래 상태를 반드시 고려한다.

- 기본 상태
- 로딩 상태
- 빈 결과 상태
- 에러 상태
- 선택 상태
- 비활성 상태
- 제출 중 상태
- 제출 완료 상태

상태가 없는 화면은 미완성으로 간주한다.

### 상태 설계 원칙

- 로딩은 짧고 조용하게 표현한다
- 빈 결과는 막다른 길이 아니라 다음 행동을 제안해야 한다
- 에러는 사용자 탓처럼 보이지 않게 작성한다
- 비활성 상태는 왜 비활성인지 힌트를 줄 수 있어야 한다
- 제출 완료 후에는 사용자가 다음에 무엇을 해야 하는지 안내해야 한다

---

## 10. 모션

- 빠르고 조용하게
- 바텀시트, 패널, 필터 노출은 150~250ms 수준의 짧은 전환
- 과도한 패럴랙스, 스프링, 튀는 애니메이션 금지
- 모션은 정보 구조를 이해시키기 위한 용도로만 사용한다
- 지도와 패널 사이의 관계를 부드럽게 이어주는 정도가 적절하다

---

## 11. 카피 톤

- 짧고 명확하게
- 부담 없는 제안형 문구
- 사용자가 다음 행동을 바로 이해할 수 있는 문장
- 광고처럼 과장하지 않는다
- 지나치게 친한 말투보다, 담백하고 신뢰감 있는 톤을 우선한다

### 문구 예시

- "근처 운동 메이트를 찾아보세요"
- "오늘 같이 운동할 사람을 등록해보세요"
- "조건에 맞는 모집글이 없어요"
- "지역을 바꿔서 다시 찾아볼까요?"
- "로그인하고 신청할 수 있어요"
- "모집 정보를 다시 확인해 주세요"

### 피해야 할 문구 예시

- "지금 당신만의 운동 여정을 시작하세요"
- "완벽한 운동 메이트를 만나보세요"
- "새로운 경험을 바로 시작해보세요"
- "놀라운 기능을 경험해보세요"

---

## 12. 콘텐츠 현실성 규칙

- 모든 화면은 실제 서비스처럼 보이는 텍스트와 데이터를 사용한다
- 버튼 문구는 행동이 명확해야 한다
- 라벨과 에러 메시지는 짧고 정확해야 한다
- 문구는 과장되거나 광고처럼 보이지 않아야 한다
- 가짜 후기, 의미 없는 숫자, 모호한 상태명은 사용하지 않는다
- 실제 사용자가 이해할 수 있는 운동 종류, 시간, 거리, 위치 표현을 사용한다
- 위치 정보는 지도 서비스답게 자연스러워야 한다

### 버튼 문구 예시

- "모임 등록하기"
- "이 조건으로 찾기"
- "지도에서 위치 확인"
- "로그인하고 신청하기"
- "다시 검색하기"

### 피해야 할 버튼 문구 예시

- "지금 시작하기"
- "더 알아보기"
- "체험해보기"
- "계속하기"  
  단, 문맥상 진짜로 다음 단계 이동 의미가 명확할 때만 예외적으로 허용

---

## 13. 반응형 기준

- 모바일 기준 폭: 약 390px
- 태블릿 / 작은 노트북: 768px 이상
- 데스크톱 기준 폭: 약 1440px

### 반응형 원칙

- 모바일 구조를 우선 설계하고, 데스크톱은 확장 개념으로 접근한다
- 모바일과 데스크톱이 서로 다른 제품처럼 보여서는 안 된다
- 단순히 요소를 늘어놓는 확장이 아니라, 정보 밀도와 탐색 효율을 높이는 방향이어야 한다
- 주요 CTA, 검색, 필터, 상세 흐름은 모든 디바이스에서 일관된 논리로 동작해야 한다

---

## 14. 완료 기준

- 모바일에서 한 손 사용성이 좋아야 한다
- 데스크톱에서 지도와 정보 패널의 균형이 자연스러워야 한다
- 같은 디자인 언어가 홈, 찾기, 등록, 로그인 전체에 이어져야 한다
- 첫 진입 시 사용자가 3초 안에 무엇을 할 수 있는지 이해할 수 있어야 한다
- CTA가 모호하지 않고, 다음 행동이 분명해야 한다
- 지도 중심 제품이라는 정체성이 흔들리지 않아야 한다
- 실제 서비스처럼 보이는 콘텐츠와 상태가 포함되어야 한다
- 금융앱 복제처럼 보이지 않으면서도, Toss-like한 정돈감과 신뢰감은 살아 있어야 한다

---

## 15. 최종 자가 검수 체크리스트

최종 결과를 내기 전에 아래 항목을 점검한다.

- 이 화면은 운동 메이트 서비스처럼 보이는가?
- 지도 중심 구조가 유지되는가?
- 첫 3초 안에 무엇을 할 수 있는지 이해되는가?
- CTA가 구체적이고 분명한가?
- 카드와 리스트가 불필요하게 반복되지 않는가?
- 금융앱이나 일반 SaaS 랜딩페이지처럼 보이지 않는가?
- 실제 서비스 데이터처럼 보이는가?
- 빈 상태 / 에러 상태 / 로딩 상태가 포함되어 있는가?
- 모바일 한 손 사용성이 자연스러운가?
- 데스크톱으로 확장되어도 같은 제품처럼 보이는가?
- Toss-like한 정돈감은 있지만 특정 서비스 복제처럼 보이지 않는가?
- 장식보다 정보 전달과 행동 유도가 우선되고 있는가?

## 16. 생성형 AI 사용 규칙

이 문서를 바탕으로 UI를 생성할 때는 아래 원칙을 함께 적용한다.

- 이 문서는 최상위 디자인 기준 문서로 취급한다
- 특정 화면 생성 시 이 문서의 원칙을 우선 적용한다
- 결과가 너무 일반적인 SaaS UI처럼 보이면 다시 수정한다
- 결과가 금융앱 복제처럼 보이면 다시 수정한다
- 지도 중심성, CTA 명확성, 콘텐츠 현실성, 상태 설계를 반드시 포함한다
- 출력은 예쁜 시안보다 실제 서비스에 가까운 화면이어야 한다

### 권장 생성 요청 예시

- "위 스펙을 모두 준수해서 홈/탐색 화면을 설계하라"
- "모바일 우선으로 만들고 데스크톱 확장 구조까지 제안하라"
- "기본 / 로딩 / 빈 결과 / 에러 상태를 함께 설계하라"
- "운동 메이트 서비스에 맞는 실제적인 카피와 데이터를 사용하라"
- "Toss-like한 정돈감은 유지하되 금융앱 복제처럼 보이지 않게 하라"

### 결과가 어색할 때 사용하는 수정 요청 예시

- "AI 템플릿 느낌을 줄이고 제품 특성을 더 살려라"
- "카드 반복을 줄이고 지도 중심 구조를 강화하라"
- "CTA를 더 구체적으로 수정하라"
- "더미 데이터를 실제 서비스처럼 교체하라"
- "토스 감성은 유지하되 금융앱처럼 보이는 요소를 제거하라"

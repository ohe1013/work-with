# Milestones

## 운영 원칙
- 한 번에 하나의 마일스톤만 활성화한다.
- 각 마일스톤은 끝났는지/아직 아닌지 분명해야 한다.
- 인접 기능을 확장하지 말고, 현재 마일스톤의 acceptance criteria를 먼저 닫는다.

---

## M0. Codex 안정화와 기준 문서 고정
### 목표
Codex가 긴 작업에서도 방향을 잃지 않도록 제품/디자인/진행 기준을 파일로 고정한다.

### 범위
- `AGENTS.md`
- `client/AGENTS.md`
- `server/AGENTS.md`
- `docs/*`
- `progress/*`
- `prompts/*`

### Acceptance criteria
- 제품 불변조건이 문서화되어 있다.
- 마일스톤이 정의되어 있다.
- 현재 진행상태를 기록하는 파일이 있다.
- 반복 실행 가능한 Codex 프롬프트가 준비되어 있다.

---

## M1. 디자인 시스템 + 앱 셸
### 목표
토스라이크 원칙을 반영한 공통 UI 토대와 앱 셸을 만든다.

### 범위
- 디자인 토큰
- 버튼, 입력, 카드, 상태 컴포넌트
- 모바일 우선 레이아웃
- 데스크톱 대응 레이아웃
- 헤더/네비게이션 구조 정리

### Acceptance criteria
- 홈/찾기/등록/로그인에 공통 디자인 언어가 적용된다.
- 모바일과 데스크톱에서 레이아웃이 모두 무너지지 않는다.
- 새 화면에서 공통 프리미티브를 재사용한다.

---

## M2. 홈/지도 탐색 완성
### 목표
지도 중심 탐색 경험을 제품답게 완성한다.

### 범위
- 지도 + 결과 리스트 연동
- 필터/검색 진입점
- 카드 선택 상태
- 상세 패널/바텀시트
- 빈 상태/로딩/에러 상태

### Acceptance criteria
- 홈에서 서비스의 핵심 가치가 바로 보인다.
- 마커와 리스트 선택이 일관된다.
- 모바일에서 바텀시트, 데스크톱에서 사이드 패널이 자연스럽다.
- 탐색 관련 placeholder가 제거된다.

---

## M3. `/find`와 `/regist` 실체화
### 목표
현재 `Home`을 재사용 중인 두 경로를 실제 목적에 맞는 화면으로 분리한다.

### 범위
- `/find` 조건 기반 탐색
- `/regist` 모집글 작성
- 폼 검증
- 제출 직전 요약
- 성공/실패 상태

### Acceptance criteria
- `/find`가 홈과 다른 명확한 목적을 가진다.
- `/regist`가 실제 등록 가능한 UX를 갖춘다.
- 두 라우트 모두 더 이상 `Home` placeholder가 아니다.

---

## M4. 인증 및 API 계약 정리
### 목표
로그인과 핵심 데이터 흐름을 안정된 계약으로 연결한다.

### 범위
- auth contract
- 사용자 상태 확인
- 모집글 조회/등록 API 계약
- 검색 contract 정리
- 프런트 API layer 정리

### Acceptance criteria
- 로그인 흐름이 더 이상 임시 상태가 아니다.
- 프런트와 서버의 주요 요청/응답 구조가 문서화되어 있다.
- 에러 처리 전략이 일관적이다.

---

## M5. 완성도 향상과 릴리즈 정리
### 목표
제품을 배포 가능한 수준으로 정리한다.

### 범위
- 접근성
- 카피 정리
- 상태 UI 마감
- 테스트 보강
- README/실행 문서 갱신

### Acceptance criteria
- 핵심 플로우가 모바일/웹 모두에서 자연스럽다.
- 눈에 띄는 placeholder, 깨진 레이아웃, 누락된 상태가 없다.
- 새 팀원이 README와 docs만 보고 작업을 이어갈 수 있다.
